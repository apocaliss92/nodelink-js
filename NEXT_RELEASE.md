### Breaking changes

- **go2rtc has been removed from the manager.** The bundled sidecar is gone — no more `go2rtc-static` binary download, no more YAML config generation, no more `/go2rtc/*` proxy. Streaming is now handled by two in-process components only: `BaichuanRtspServer` plugged into a single shared `LocalRtspMux` (RTSP, default port `8554`) and `BaichuanWebRTCServer` (in-process WebRTC via werift, for the in-browser preview).
- **HLS, MSE, MJPEG, transcoded MP4 and transcoded snapshot outputs are gone.** They only existed because go2rtc generated them. Consumers must switch to RTSP (every NVR / Frigate / Home Assistant card / ffmpeg client speaks it natively) or to the WebRTC preview built into the manager. CGI snapshots from the camera continue to work.
- **Bridge-mode Docker port mappings change.** Drop `11984`, `18554` and `18555`. Keep `3000` (UI/API), `8554` (RTSP + Frigate two-way audio path) and the WebRTC ICE UDP range configured in **Settings → WebRTC (ICE)**. `network_mode: host` continues to work without changes.
- **Settings migration is silent on first boot.** `restreamer`, `settings.go2rtc.*`, `settings.webrtc.preferredBackend` and the legacy `talk` block are stripped from `settings.json` automatically (Zod drops unknown keys; marker migrations force the rewrite). The Settings UI is shorter: the Restreamer tab is replaced by a smaller RTSP tab with the mux port and the Frigate config builder.
- **Frigate config builder targets the new endpoint.** The emitted YAML uses `rtsp://<host>:<localRtsp.port>/<cameraName>/<profile>` for video and `rtsp://<host>:<localRtsp.port>/<cameraName>?backchannel=1` for two-way audio — both on the same port.

### Features

- **A clip's bytes can be consumed AS THEY ARRIVE.** Every download entry point returns `Promise<Buffer>`, so a consumer could not begin until the last byte had landed — downstream that meant a clip was downloaded whole, muxed, read back and base64'd before a single frame could be shown. New optional `onChunk(chunk: Buffer)` on `sendBinary` (cmd 5) and on `fileInfoListReplayBinaryDownload`, called with each decrypted chunk before it is accumulated. **The chunks were always there**, one frame at a time, already decrypted; nothing exposed them. The captured sequences say where the time is NOT: on a standalone the last byte of a 101 s / 1.8 MB clip lands at **1 702 ms with a 59 ms largest gap**, against **7.9 s** measured for the same volume through a consumer that waits for the Buffer. Strictly additive — a caller that passes no callback gets the same Buffer byte for byte, asserted over both the standalone and hub captures. A callback that throws fails the transfer loudly rather than returning a truncated Buffer that looks complete.
- **Recordings carry the camera's wall clock explicitly.** Every FileInfoList search window, CoverPreview window and file-name timestamp is the camera's local time with no offset; the library used to read and write them with the host's `Date` accessors. New constructor option `recordingsTimeZone` (IANA, e.g. `Europe/Rome`) and a per-call `timeZone` on `getVideoclips`, `getVideoclipThumbnail`, `getVideoclipThumbnailJpeg`/`JpegRaw`, plus `parseRecordingFileName(name, { timeZone })` and `parseRecordingFilesFromXml(xml, { timeZone })`. Helpers exported: `wallClockParts`, `dateFromWallClock`, `endOfWallClockDay`, `isKnownTimeZone`. Omitting the zone keeps the previous host-local behaviour. The one-camera-day clamp in `getVideoclips` now ends the day in the camera's zone.
- **A downloaded clip has sound.** `downloadRecordingDemuxed` now returns `audio: RecordingAudioTrack | null` beside `annexB`, plus the frame rate a mux needs (`stats.fps`, `stats.durationSeconds`, `stats.infoFps`, `stats.fpsSource`) and `stats.audioBytes`. **The cmd 5 download always carried the audio** — it is in the same BcMedia stream as the video and this method simply registered no `onAudioFrame`, so a consumer wanting sound had to go through `getRecordingVideo`, which muxes `frag_keyframe+empty_moov+default_base_moof` and therefore costs the `moov`-first seek and the known duration an MP4 file is wanted for. Measured 2026-09-20, read-only, one session per device: a 2 s clip on a standalone E1 Outdoor PoE v3.1.0.5223 came back as **1 967 336 B in 2 662 ms** with 51 H.264 access units and **32 AAC frames (16 608 B)**; a 43 s clip on a Home Hub v3.3.0.456 child came back as **11 680 272 B in 9 074 ms** with 661 H.265 access units and **688 AAC frames (357 072 B)**; a 27 s standalone clip, 21 779 592 B in 6 799 ms, 676 AUs + 426 AAC frames. Both cameras speak **AAC-LC, 16 kHz, mono, one ADTS frame per BcMedia packet (519 B)** whose `frame_length` equals the packet, so `audio.data` is a complete elementary stream: `ffmpeg -f aac -i … -c:a copy -bsf:a aac_adtstoasc` takes it as a second input and the output keeps `-movflags +faststart`, a real duration and byte-Range. Verified end-to-end on both devices — `moov` before `mdat`, tracks 0.4 ms apart over 27 s and 21 ms over 44 s. No camera here produced ADPCM; if one does, `format` is `adpcm`, `sampleRate`/`channels` are `null` (the wire does not say) and it must be transcoded, not copied. Nothing about the transfer changed: the idle window is untouched, and the audio arrives interleaved with the video, not in a tail.
- **Two things the download's own headers get wrong, now corrected and reported.** (1) `InfoV1`/`InfoV2` `fps` is the FILE's nominal rate, not the delivered one — the hub child declares **30** and delivers **15.019** (661 AUs over 43.943 s of timestamps); muxing at the declared rate makes the video half as long as its own audio. The access-unit timestamps are the authority and `stats.fpsSource` says which was used, so a fallback never looks like a measurement. New `estimateVideoTiming` / `roundRecordingFps`, shared with `getRecordingVideo` so the two paths cannot drift apart. (2) On that hub child **every I/P packet declares `H264` in its BcMedia header while the payload is H.265** — `videoType` comes from `detectVideoCodecFromNal`, never from the header.
- **`BcMediaAnnexBDecoderStats.audioBytesOut` counts whether or not anyone is listening.** It was incremented only inside the `onAudioFrame` branch, so the one statistic that answers "did this clip have sound?" read 0 for every caller that had not already decided to collect the audio.
- New `test/fixtures/recordings/{standalone,hub}/download-5-bcmedia-audio.bin` + `-meta.json`: the first 40 BcMedia packets of a real download per topology, headers byte-for-byte, AAC ADTS headers kept and their compressed bytes zeroed, video payloads replaced by synthetic Annex-B NALs of the detected codec. Pinned by `test/lib/recordings-download-audio.test.ts`.
- **`downloadRecording({ idleTimeoutMs })`** and `DEFAULT_RECORDING_DOWNLOAD_IDLE_MS` (2 000 ms). Nothing on the wire marks the end of a cmd 5 transfer (responseCode 200 on the stream header, 0 on every chunk, never 201, no trailing frame), so completion is an idle window — and it was a fixed 15 s. Measured 2026-09-20 on an E1 Outdoor PoE v3.1.0.5223 and a Home Hub v3.3.0.456: a 101 s / 1.8 MB clip fully arrived in 1 702 ms with a 59 ms largest inter-chunk gap, then waited 15 s. Every download is now ~13 s faster; raise the window per call on a slow link.
- **Native-only standalone recordings need no UID from the caller.** In `nativeOnly` mode `ensureUidForRecordings` now asks cmd 114 `GetUid` (7 ms) on a standalone camera and caches the answer, instead of throwing. Never on an NVR/Hub, where cmd 114 is the hub's own UID — a child channel's UID still comes from the cmd 145 push or the caller.
- **`getDayRecords` works — the recording calendar (cmd 142).** New signature `getDayRecords({ year, month, channel?, uid?, timeoutMs? })` → `{ index, channelId, days: [{ day, type }] }`, and `getDayRecordsForChannels({ year, month, entries: [{ channel, uid }] })` for several channels of a Hub in ONE request. The request is a calendar-month window plus one `<DayRecord>{ index, channelId, uid }` per channel, sent as a body with no Extension; the reply's `<dayType index>` is the day of month minus one and an absent day has no footage, `type` is an open vocabulary (`normal` seen). Captured from the official app on a standalone E1 Outdoor PoE (v3.1.0.5223) and on a Home Hub (v3.3.0.456, child ch 0), verified live on hub channels 0/1/3 (50–60 ms each, 393 ms for three at once). On a Hub the UID selects the camera and the channel is echoed; on a standalone the UID is ignored. Builders/parser exported (`buildDayRecordsXml`, `parseDayRecordsXml`, `daysInMonth`). The old `getDayRecords(channel?)` sent no body and always answered 400.
- **`getVideoclips` sends the official app's full record-type filter by default** — 16 types (`DEFAULT_RECORDING_SEARCH_RECORD_TYPES`, adds `crossline,intrusion,loitering,legacy,loss`) plus the `<fileRecordType>` item list (`DEFAULT_RECORDING_SEARCH_FILE_RECORD_TYPES`, 19 items), byte-identical to the app's open on a standalone E1 Outdoor PoE and on a Home Hub child. The old default was eleven types with spaces; a narrower list silently returns fewer files. New `fileRecordTypes` param. Note the app asks the SUB and the MAIN stream as two searches and the two file sets are twins with different names (start seconds differ by 0–4 s; 168 of 170 pairs within 3 s on one day): a `streamType` search lists one stream's files only.
- **`searchAlarmVideos` — the alarm WINDOWS inside a camera's recordings (cmd 272/273/274 `<findAlarmVideo>`).** Not a second `getVideoclips`: that one answers with FILES, this one with the event windows inside them. Measured live on a standalone E1 Outdoor PoE (v3.1.0.5223) on 19 September: **1 271 windows over 539 files, 1-10-and-up-to-13 per file, every one contained in its own file's window**, and the union of a file's `alarmType`s equal to the file's `recordType` on 501 of the 539. `fileName` is exactly a `getVideoclips` `name`, so the two surfaces **join** on it. Three things the wire settles: the family carries an `<Extension><channelId>N</channelId></Extension>` (cmd 14/15/16 carry none); the 273 get and the 274 close send the same body byte for byte; and **`streamType` is numeric here and selects the FILE SET** — `0` returned all 539 main-stream names, `1` all 539 sub-stream ones (the app sends 0). The search is **one camera-local day and the firmware enforces it by dropping the rest** (an 18→19 September window answered 462 windows all dated the 18th, standalone and hub child alike), so `end` is clamped like `getVideoclips` and the clamp is logged. `alarmType` is parsed as an open vocabulary, never enumerated.
- **`searchEventLog` — the Home Hub's cross-channel EVENT list (cmd 516/517/518 `<findEventLog>`).** One search across every child, each row carrying its class, and not bounded to a day: **59 events over three children and three days in 2 372 ms**, 1 886 events over 20 days in 11 908 ms, against a per-channel file listing that carries no class at all. **Hub only** — a standalone answers the open with an empty body (17 ms) and the method refuses by name instead of reading the silence as "no events". Two readings the live probe overturned: the window **must** be written backwards (`startTime` = the later instant) — written forwards it answered **zero rows** — and `desc` is not what orders the rows; and the channel selection travels as the `<devices>` list, **not** `chnbits`, which answered identically at 3 and at 0 while cutting `devices` to one child cut 59 events to 10. `hasRecFile` is false on a large minority of rows (515 of 1 886), so an event is not a promise of a clip. Paging uses the handle the OPEN returned (a get's reply carries a different one, recorded and unused); repeats across page boundaries are deduped on `(uid, logicChn, startTime, alarmType)` with the device's order preserved. `devices` defaults to every child the cmd 145 push knows a UID for.
- **Command map:** named from the 2026-09-20 captures — `BC_CMD_ID_REPLAY_SEEK` (123, `<ReplaySeek>{ channelId, seq, seekTime }`; `BC_CMD_ID_CMD_123` kept as an alias), `BC_CMD_ID_GET_NETWORK_CONFIG` (76, `Dhcp/AutoDns/Ip/Dns`), `BC_CMD_ID_GET_CHANNEL_VERSION_INFO` (318, per-channel `<VersionInfo>`, already sent as a literal by `getChannelInfo`), and `BC_CMD_ID_CMD_192_OPAQUE` (192, empty body both ways, purpose unknown). **272/273/274 are renamed `BC_CMD_ID_FIND_ALARM_VIDEO_OPEN/GET/CLOSE`** — the body is `<findAlarmVideo>` and it answers alarm windows, so the old `BC_CMD_ID_FIND_REC_VIDEO_*` said the opposite of what the command does; the old names are kept as deprecated aliases, as `BC_CMD_ID_CMD_123` is. `BC_CMD_ID_FIND_EVENT_LOG_OPEN/GET/CLOSE` (516/517/518) keep their names — they already matched the body.
- **Fixtures and tests for the whole recordings surface** (`test/fixtures/recordings/`, `test/lib/recordings-*.test.ts`): decrypted FileInfoList exchanges, the cmd 145 push, sanitised CoverPreview payloads (`1001` and `1002` headers) and a full cmd 5 frame sequence, from a standalone E1 Outdoor PoE and a Home Hub child. The surface had none. The two new search families are pinned the same way — every request reproduced byte-for-byte against the app's capture, the multi-page standalone case, and the standalone's empty-body answer to cmd 516 as a fixture of its own.

- **PTZ guard point** — the "monitoring point" of the official app, and this vendor's real *home*. A guard point is a position the camera returns to on its own after a timeout **and** a position it can be sent to on command; nothing else in the Baichuan PTZ surface offers one, so a consumer wanting "go home" had to pick an arbitrary preset slot and hope the installer had used it that way. The library already declared the ability leaf (`supportGuardPointImage`) and mapped none of the commands. New: `api.getPtzGuard()`, `api.setPtzGuard({ enabled, timeoutSeconds, setPosition })` and `api.goToPtzGuard()`, plus the builders and parser (`buildPtzGuardSetXml`, `buildPtzGuardGoXml`, `buildPtzGuardExtensionXml`, `parsePtzGuardXml`) and the command ids `BC_CMD_ID_PTZ_GUARD` (331, `setGrd` / `toGrd`) and `BC_CMD_ID_GET_PTZ_GUARD` (332).

  Captured from the official app against an E1 Outdoor PoE (firmware v3.1.0.5223) and decrypted with the session key derived from the login handshake, so the payloads are observed rather than guessed. Two wire details are reproduced verbatim because a firmware parser cares: floats are **scientific with a two-digit exponent** on the write (`0.000000e+00`, i.e. C's `%e`, not JavaScript's one-digit `toExponential`) and plain on the read, and the **read** extension carries `<chnType>` while the **write** extension does not.

  `setPosition` (`needSetPos`) is sent only when explicitly pinning the point to the head's current position — in the capture it appeared on the first set and never again, and re-sending it on every edit would silently move a position the operator had already placed. `parsePtzGuardXml` returns `null` for an unreadable reply rather than a default: `bvalid` is what tells a consumer whether a guard point exists at all, and it is independent of `benable`.

  Not observed, and therefore not written: only `mode: global` ever appeared, and `xpos/ypos/height/width` were zero in every frame including the enabled ones.

- New **power source switch** for battery cameras and battery doorbells: `api.switchPowerSource("adapter" | "battery", { channel, dryRun })` wraps Baichuan cmd **805 `SwitchBatteryAdapterMode`** — the command the Reolink app uses for "Wired Power" vs "Battery Power" (distinct from the wired *working* mode / Continuous setting). Useful when the app fails its pre-flight power read while the device is wired and never reaches the switch. Companion helpers: `api.getPowerSource()` (current source from `BatteryInfo.adapterStatus`), `api.probePowerSourceSwitchSupport()` (authoritative dry-run probe) and the new `DeviceCapabilities.hasPowerSourceSwitch` hint (`support.items[].battery > 0 && batteryMode & 32`). Successful firmwares answer 200 with an empty body — verify with `getPowerSource()`. See [documentation/baichuan-api/battery.md](./documentation/baichuan-api/battery.md#power-source-wired-vs-battery).
- Stream **analyzer** now scores server-side health deterministically. Each report gains:
  - `video.droppedFrames` / `video.duplicatedFrames` (parsed from ffmpeg's `dup=` / `drop=` counters in the progress line — previously not captured)
  - `video.expectedFps` (from the camera's own `getStreamMetadata.frameRate` for the analyzed profile)
  - `verdict: { severity, reasons, fpsDeltaPct, dropRatePct }` — a top-line `ok` / `warn` / `error` plus the list of signals that contributed. Lets the UI answer "is the server stream healthy?" without forcing the reader to interpret every field.
- **RTSP backchannel is always on.** The `talk.enabled` toggle has been removed; the multiplexed backchannel listener attaches to the LocalRtspMux at boot and starts serving every connected camera under `/<cameraName>` automatically.
- New **Capture** page (server + UI) drives a live tshark capture against a chosen camera, parses Baichuan frames in real time, classifies cmd_ids as known/unknown, and walks the user through the auth handshake checklist (started → nonce captured → login successful). Sanitized JSON export and redacted `.pcapng` export — login XML bodies wiped, TCP checksums recomputed, nonce kept so maintainers can decrypt locally. Past captures persist under Reports → Packet Captures.
- Docker image now ships with `tshark` (Alpine package) and the `setcap` for `dumpcap`; compose file documents the `cap_add: NET_RAW, NET_ADMIN` requirement.
- New **Stream settings** panel in the camera detail tab. Reads `getEncOptions` (cmd_146) + `getStreamMetadata` (cmd_56) and renders one editor per profile (main / sub / ext) with selectors populated only from values the camera reports as supported. Per-profile Apply button calls `setEnc` and re-reads on success.
- New `api.onObjectDetections(cb, { channel?, profile? })` / `offObjectDetections(cb?, { channel?, profile? })` API mirroring `onSimpleEvent`. Listeners and substreams are tracked per `(channel, profile)` tuple — required so NVR/Hub child cameras subscribe on their own channel; defaults are `channel: 0`, `profile: "sub"`. Reference-counted lifecycle ensures the matching stream is running on the first listener for a tuple and closes it on the last. Every event carries the AI class label (people / vehicle / animal / face), confidence and normalized box coordinates — no need to manage a video stream yourself.
- Decoded AI Mark `additionalHeader` (TLV chain + LZ4F-compressed inner payload) end-to-end. Boxes are now emitted with class label and confidence, mirroring the SDK's own dispatch via the static `s_tlv_types_map` table.
- Manager UI: reboot camera button in the right detail panel (with confirmation step).
- Manager UI: snapshot download button — captures a JPEG from the camera and downloads it directly to the browser.
- Manager UI: detection box overlay with per-class colours (people=cyan, vehicle=violet, animal=orange, face=pink), toggle checkbox on the floating stream panel.
- Manager UI: detection SSE is lazy-attached — `onObjectDetections` is activated only when the first overlay client connects and stops when the last disconnects, so idle UIs cost zero extra substream bandwidth.

### Fixes

- **A cmd 5 replay can no longer be handed another transfer's frames.** A consumer opened a replay, the peer closed it after 236 ms, and a second replay on the same host opened 1 ms later was given the first one's in-flight frames — +5 access units, +5 audio frames and a duration short by 3.69 s against a clean run of the same file, and a frame-rate probe downstream that read five timestamps at ~3.6 s then eleven from zero and could not measure the rate. Three things made it possible, and the capture says which: **`msgNum` is `0` on every cmd 5 frame in both directions** (Reolink app, 5 937 cmd 5 frames, standalone 2026-09-22; same through a hub 2026-09-20), so it never discriminated anything; the header **channelId IS the session handle** — the app mints a fresh one per replay and the camera echoes it on every chunk, **on a hub child too** (105, 111, 124, 142, 163, 170) — and this library pinned it on the hub/NVR download path; and the listener locked on whatever the FIRST frame it saw carried rather than on the handle it had asked for. Reproduced live on a mains standalone: pinned, the successor swallowed its predecessor's tail indistinguishably; minted, the successor locked onto 243 residue frames and **rejected all 4 237 of its own**, returning the wrong clip. Now: the handle is minted per transfer on every topology, a minted transfer **pre-locks the handle it requested**, a superseded transfer refuses every further frame, and both refusals are counted and logged (`foreign-channel` / `superseded`). A transfer that times out having accepted nothing names the handles it rejected instead of failing blind. Verified end-to-end on the real download path: abandon a transfer mid-flight, download the same clip again, **3 097 776 bytes byte-identical to the clean run**, on three distinct handles. `headerChannelIdOverride` remains as an escape hatch for a firmware that needs a pinned handle.
- **An abandoned replay is now ENDED at the camera, not just dropped locally.** A cmd 5 replay is a session and nothing in the data stream closes it: the only lever a consumer had was throwing from `onChunk`, which failed the transfer here while the camera kept sending. Measured live (303 s clip, mainStream): abandoned with no stop, **8 126 more frames over 3 475 ms**; with the cmd 7 stop — `rc 200` in 67 ms — **zero**. `fileInfoListReplayBinaryDownload` now sends that stop on every exit, success or failure, and then waits for the wire to go quiet, because the ack is not the end at the camera: four of eleven stopped sessions in the app's own capture were still delivering when the ack came back (26–91 further frames). New `BaichuanClient.drainReplayFrames({ quietMs, maxMs })`, and `DEFAULT_REPLAY_STOP_DRAIN_QUIET_MS` / `DEFAULT_REPLAY_STOP_DRAIN_MAX_MS`.
- **The replay stop names its channel.** `buildReplayStopNameFromFileName` hardcoded the `01` prefix of `CCYYYYMMDDHHMMSS`. Measured: a hub's second child (`<channelId>1</channelId>`) is stopped with `0220260918181308` while the first child's stops are `01…` — the prefix is the two-digit 1-based channel. It takes an optional `channel` (default `0`, so every existing caller keeps what it had) and both replay-stream stop paths now pass theirs.
- **The replay documentation was re-derived from the captures and two of its claims were wrong.** `documentation/baichuan-api/recordings.md` said "eight replay requests" and "591 stop payloads" (really 12 and 11), and "there is no in-session seek" — the app in fact sends **cmd 123 `ReplaySeek`** before every replay, carrying a `<seq>` and a wall-clock `<seekTime>`. What holds is that a new position is a new session.

- `getVideoclipThumbnailJpeg` and `getVideoclipThumbnailJpegRaw` accept `uid` (and `isNvr`, `endTime`, `timeZone`). Without it a Home Hub child whose cmd 145 push had not arrived got a CoverPreview without `<uid>` and answered 400 while the raw call with an explicit `uid` succeeded (Home Hub v3.3.0.456, ch 0 and 1).
- `getVideoclipThumbnail`: a window whose end is not after its start is widened to the 10 s default — the camera refuses `end == start` with 400 (E1 Outdoor PoE v3.1.0.5223, a 0 s clip).
- `getVideoclips`: removed a header `channelIdOverride` that could never fire (it was keyed on a `channel` the FileInfoList helper never passes). The rule it hid is now stated where it is enforced and pinned by a test: cmd 14/15/16 carry the channel in the XML body only and the header stays hostChannelId 250 on both topologies.
- `documentation/baichuan-api/recordings.md` described parameters that do not exist (`startTime`/`endTime` on `getVideoclips`, `filename` on the thumbnail and download calls, `{ year, month }` on `getDayRecords`, `{ rtmpUrl, httpUrl, rtspUrl }` playback URLs). Rewritten from the code.

- **Dead RTSP stream for hours after a camera reboot (#37).** A camera reboot left a half-open TCP control socket that `isSocketConnected()` could not detect (the socket is not `destroyed`), so the keepalive ping timeout was swallowed and the connection stayed stale-"alive" — the event watchdog only re-subscribed events and never rebuilt the socket or the video stream, leaving Frigate's RTSP source dead while recovery spun at the 300s backoff cap. Now an unanswered TCP keepalive ping is treated as a hard liveness failure: after a couple of misses the half-open socket is torn down (firing the normal `close`/reconnect path), and the event watchdog escalates a down control socket to a full `ensureConnected()` reconnect. Battery/UDP cameras keep the original skip behaviour (a down socket is their normal idle/sleep state).
- **Dropped / choppy frames in downstream consumers despite a clean source (#30).** The per-client RTSP delivery path ignored TCP write backpressure, so a keyframe burst (~94 FU-A writes for a 100 KB+ IDR) could flood and coalesce on the socket and arrive jittered — the consumer (Frigate/ffmpeg) reported dropped/late frames even though the server-side stream analyzer showed zero drops. The feed loop now awaits the client socket's `drain` after each access unit, and a previously-unreachable send-buffer hard cap (8 MB) now actually disconnects a runaway/too-slow client. Not tied to go2rtc — applies to any TCP-interleaved RTSP consumer.
- Multi-class wrapper dedup for detection boxes. Reolink cameras emit the same box in multiple class arrays (people + vehicle, or all three for animals); the decoder now dedupes by exact coords and picks the most specific class (animal > people > vehicle), matching what the SDK app does.
- Build hardening for nested TLV: walker now tolerates non-LZ4F box-length variants (type=4 len=13/14, type=2 len=10) and recovers gracefully from malformed sub-trees.
- WebRTC native H.265 4K mainStream: client now reassembles chunked DataChannel messages before feeding the WebCodecs decoder. Previously the decoder failed with "A key frame is required after configure()" because each chunk was decoded as if it were a complete frame. Server prepends a uniform 4-byte chunk header `[u16 BE chunkIndex][u16 BE totalChunks]` to every binary message so the client can reassemble unambiguously.
- Detection box overlay no longer stretches into the letterboxed black bars when the stream container aspect ratio doesn't match the camera frame. Boxes are now mapped into the actual displayed picture rect using the video's intrinsic dimensions.
- WebRTC inline player gains mute/unmute and fullscreen controls that work for both modes (HTML5 `<video>` for RTP H.264 and `<canvas>` for WebCodecs H.265). Previously the canvas mode had no playback controls at all.
